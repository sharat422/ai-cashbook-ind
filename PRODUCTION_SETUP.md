# Production Setup — going live for real users

This guide takes the app from "works in testing" to "ready to test with live
users": a persistent database, real AI, and WhatsApp delivery. It documents
**every environment variable** — what it's for, whether it's required, and
exactly how to obtain it.

> The backend degrades gracefully: with a variable blank, that feature falls
> back (heuristic AI, empty receipt draft, in-app-only notifications). Nothing
> crashes. So you can turn features on one at a time.

---

## 0. Two environments: staging vs production

`render.yaml` defines **two independent backends** so test data and real user
data never mix. Each has its own web service, its own PostgreSQL, and its own
`JWT_SECRET` (a token from one is invalid in the other).

| | **Staging** | **Production** |
|---|---|---|
| Service | `smart-cashbook-api` | `smart-cashbook-api-prod` |
| URL | `https://smart-cashbook-api.onrender.com` | `https://smart-cashbook-api-prod.onrender.com` |
| Database | `smart-cashbook-db-staging` | `smart-cashbook-db-prod` |
| Region | Oregon (US) | Singapore (near India) |
| `DEBUG` | `true` (login with OTP `123456`) | `false` (real auth — see §7) |
| Use it for | USA testing now, iterating | India final test + launch |

**Apply both:** Render → **New +** → **Blueprint** → this repo → **Apply**. One
blueprint manages both environments. Set each service's secrets (§4–§6)
separately in its own **Environment** tab.

**Point an app build at an environment.** Both CI workflows default to the
staging URL (from `.env.example`). To build against **production**, set an
`API_BASE_URL` variable in the Codemagic workflow's environment — the build
overrides `.env` automatically (see the "Seed .env" step in `codemagic.yaml`):

| Build | `API_BASE_URL` in Codemagic |
|---|---|
| Staging (default) | *(unset)* → `https://smart-cashbook-api.onrender.com` |
| Production | `https://smart-cashbook-api-prod.onrender.com` |

> Tip: the cleanest setup is two Codemagic workflows (or two env groups) —
> "staging" and "production" — so each always builds against the right backend.
> Ask and I'll wire them.

> Migrating from the earlier single-service blueprint? Re-applying creates the
> two new databases; the old `smart-cashbook-db` (if you created it) can be
> deleted — its staging data is disposable.

## 2. `DATABASE_URL` — persistent PostgreSQL (required for live users)

SQLite was fine for testing but resets on every redeploy. The updated
`render.yaml` provisions a managed **PostgreSQL** database and injects its
connection string automatically.

**To apply:**
1. Render dashboard → **New +** → **Blueprint** → select this repo → **Apply**.
   Render creates `smart-cashbook-db` (Postgres) and wires `DATABASE_URL` into
   the web service. Tables auto-create on first boot — no migration step.
2. Verify: service **Logs** show a successful start; `…/health` returns
   `{"status":"ok"}`.

*Notes:* The free Postgres plan is 1 GB and is removed ~90 days after creation
— upgrade the DB plan before real production. The code normalizes the
`postgres://` scheme and enables `pool_pre_ping` (see
[backend/app/database.py](backend/app/database.py)).

## 3. `JWT_SECRET` — token signing (required)

Auto-generated by Render (`generateValue: true`). Nothing to do. If you ever
rotate it, all existing logins are invalidated (users re-login). Never commit a
real secret.

## 6. WhatsApp Business Cloud API — outbound notifications

Powers `POST /notifications/whatsapp` (daily summary, reminders). Blank → the
endpoint returns 503 and the app uses the in-app inbox only.

### 6a. Get the credentials (test path — ~15 min)
1. Go to <https://developers.facebook.com> → **My Apps → Create App** → type
   **Business** → finish.
2. In the app, **Add product → WhatsApp → Set up**.
3. Open **WhatsApp → API Setup**. You'll see:
   - a **test phone number** (Meta-provided sender),
   - a **Phone number ID** → this is `WHATSAPP_PHONE_NUMBER_ID`,
   - a **temporary access token** (valid 24h) → this is `WHATSAPP_ACCESS_TOKEN` for testing.
4. Under **"To"**, add your own WhatsApp number as an allowed **recipient** and
   confirm the code (test mode only sends to numbers you've added).
5. Render → Environment → set `WHATSAPP_ACCESS_TOKEN` and
   `WHATSAPP_PHONE_NUMBER_ID` → **Save**.

### 6b. Make it permanent (production path)
- **Permanent token:** Business Settings → **System users** → create a system
  user → **Add assets** (your app) → **Generate token** with
  `whatsapp_business_messaging` + `whatsapp_business_management` scopes. Use
  that as `WHATSAPP_ACCESS_TOKEN` (doesn't expire).
- **Your own sender number:** WhatsApp → **Phone numbers** → add & verify your
  business number; use its Phone number ID.
- **Business verification:** complete Meta Business verification to lift limits.

### 6c. ⚠️ Important WhatsApp policy limit
Free-form **text** messages (what this endpoint sends) only deliver **within a
24-hour window after the user messages your number**. For business-initiated
messages **outside** that window (e.g. a scheduled daily summary), WhatsApp
requires a pre-approved **message template**. For that you'd create/submit a
template in **WhatsApp Manager → Message Templates** and switch the send to the
`template` type. The current MVP send is text — perfect for reminders the user
prompts, and for testing; add templates before relying on unsolicited pushes.

### 6d. Turn it on in the app
The app only calls the endpoint when its **own** flag is on:
1. In the mobile build's `./.env`, set `WHATSAPP_ENABLED=true`.
2. Rebuild the app (env is inlined at build time).
3. Verify: log in, open **Daily Summary → Send summary now** → the message
   arrives on WhatsApp (or check `GET /api/v1/notifications/whatsapp/status`
   returns `{"configured": true}`).

## 7. ⚠️ `DEBUG` / `MASTER_OTP` — the login caveat

`DEBUG=true` makes the backend accept the master OTP `123456` for **any**
number (no SMS provider needed). This is how you log in during testing.

**For live users this is a serious risk** — anyone can log in as any number
using `123456`. Because a real SMS OTP flow is intentionally out of scope here,
keep this configuration **only for a controlled group of test users**. Before a
public launch you must wire a real SMS provider (e.g. MSG91/Twilio), stop
accepting the master OTP, and set `DEBUG=false`.

Also flip the app's temporary login bypass off: set
[`bypassAuth`](src/config/constants.ts) to `false` so users actually
authenticate.

## 8. Deploy & verify checklist

1. ☐ `render.yaml` applied → web service + Postgres live.
2. ☐ `…/health` → `{"status":"ok"}`; `…/docs` loads.
3. ☐ Secrets set in Render: (optional) OpenAI, Anthropic, WhatsApp.
4. ☐ App `./.env`: `API_BASE_URL` = the Render URL; `WHATSAPP_ENABLED` as desired; `bypassAuth=false`.
5. ☐ Rebuild the app (codemagic) → install from TestFlight.
6. ☐ Smoke test (see [MANUAL_TESTING.md](MANUAL_TESTING.md) §Regression).
7. ☐ Automated suites green: `npm test` and `cd backend && python -m pytest`.

## 9. Known limitations before "real" production
- **Login uses a master OTP** (see §7) — wire real SMS before public launch.
- **Uploaded receipt images** live on the instance disk (ephemeral) — move to
  S3/Cloudinary for durability.
- **Free Render** web + DB sleep/expire — move to paid plans for always-on.
- **WhatsApp text** needs the 24h window or an approved template (§6c).
